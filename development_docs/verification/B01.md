`control.checkpoints/build-timing` 保存第一次进入本地封存前的 `build_started_at`，重试不覆盖。保存使用两秒有界 context；失败只报告固定诊断，缺少起点不能生成完整可用时间。恢复任务缺少该检查点时不从任务创建时间补造。

只有成功进度已确认、正式 outbox 已 applied／confirmed、M/S 当前槽位分别具有 ready 证据，以及正常 API Key 请求四接口均返回目标 `X-SICP-Combination`，才写 `usable_at`。探测前后重读活动元数据；旧组合、错误响应、取消、重定向或缺失证据不能写终点。总探测最多 45 秒，每个 HTTP 请求最多 10 秒、响应最多 1 MiB，不输出响应原文或凭据。读完响应后仅释放自己收到的分页 token，删除条件绑定 token／组合／接口／请求条件，不清除用户快照。

探测失败不撤销已确认发布、不将成功任务改成失败、不无限阻塞调度；该轮没有 `usable_at`，属于不完整样本。恢复完成路径在释放所有权前执行缺失的探测；所有权已释放后不另起无限重试任务。

阶段事件包含 `sealing`、`input_check`、`prepare_target`、`merge_table`、`target_check`、`write_copy`、`write_table`、`validate_copy`、`content_check`、`content_table`、`index_check`、`business_check`、`old_copy_check`、`route_shift`、`drain`、`publish`、`publish_confirm`、`confirm_progress`、`usable_probe`。复用不伪造执行，未排空不记录成功；逐表写入结束包含关闭文件及账本确认。

每次执行有独立且脱敏的 `session_id`；同会话／同作用域的 `attempt`、`cumulative_ns` 区分本次与累计，跨进程不伪造单调时钟。持久 UTC 区间包含中断／恢复等待；父子及并行阶段重叠，不能相加得到 T。

## 计数定义

计数器只在 context 内聚合，不逐行写控制库、不自行创建采集 goroutine。事件沿用 Sanitizer、持久缓冲、独立日志库；任务、会话、组合和候选标识仍经 HMAC 脱敏。

| 字段 | 口径 |
| --- | --- |
| `rows_read` / `bytes_read` | 源页、目标、排序文件和数据库读取；重复扫描重复累计。文件计载荷，数据库计恢复字段值，不等同网络流量 |
| `rows_written` / `bytes_written` | 目标文件成功写入及数据库成功提交批次；文件含换行，数据库计绑定源值字节，按阶段区分 |
| `batches` | 目标文件写批、数据库写批及读批次数 |
| `file_validations` | 输入／目标／排序文件 checksum 核对次数；完整复核遍数另见 input_check／target_check 事件 |
| `decodes` | 构建路径 DecodeRecord 调用次数，包含重复校验解析；上游采集不计入构建 |
| `sql` | 工作 context 内 Exec／QueryRow／Query 次数，含失败尝试；不计驱动内部事务指令和异步日志投递 |
| `cases` | 成功执行的业务案例或接口探测次数 |
| `lock_wait_ns` | 执行／槽位／快照锁获取 RPC 的单调耗时，含往返开销；不是持锁时间或纯 PG 等待 |
| `buffer_peak_bytes` | 跟踪的源页、目标块、排序／输出、SQL 批载荷峰值；父阶段计并发存活量，不冒充 RSS／全部 Go 对象大小 |
| `temporary_disk_peak_bytes` | 本构建创建的排序文件存活峰值，删除成功才释放；累计写放大见 spool_bytes_written |

溢出／负值置 `invalid`，不回绕；基准拒绝 invalid 指标。RSS、CPU、容器、文件系统采样在隔离 runner 单独输出。前台缺少构建 context 时不增加批缓冲遍历。

## 容量与 GitHub 入口

`internal/buildfixture` 的 b01-v1 固定十四表 **2,592,390 行**，seed=73，按需生成最多 1000 行 HTTP 页。场景为初始化、各表 ceil(1%)（至少一行）变化、各表 100% 替换；全量替换保持合法键和关联，全部行有新源时间。覆盖多学期、学生／课程／教学班基数、前导零、null／缺字段、3／3.0／"3"、变长中文字段、重复引用课程号和多教师。

独立参考只依赖标准库 JSON／SHA256，不调用生产 merge／Canonical；按固定宽度主键升序生成最终摘要，增量包含未返回的旧行。报告保存完整 fixture 参数（含 Epoch／ChangedAt），可重现时间字段。容量运行逐行计算实际字节，要求 0.48—0.60 GB；**实际值待 GitHub，不把要求范围当实测**。

`tests/integration/build_performance_test.go` 使用六个独立 PG 数据库、隔离 Redis、真实 collector／文件／worker／查询 HTTP。源页实际持久保存后进入封存，不伪造 ready／账本；容量测试正常运行生产日志 dispatcher，防止测试自身填满日志缓冲。参考生成和 worker 全部耗时分别报告，T 仅取持久起止。

- Linux CI 的 unit 执行 BT01、race、vet；integration 的 I05 包含小规模三场景和失败探测。
- B01 build baseline 在本分支 push 后运行容量基准，也可手动启用 CPU／heap profile。正式容量计时不带 race，profile 标注诊断。
- `scripts/check-build-performance.sh` 限定隔离 GitHub 环境，编译在资源计时外，退出停止采样。
- 工件 `b01-baseline-<SHA>`：runner.json、capacity/stages.json、resources.log、process-resources.txt、退出码和日志；小规模结果在 linux-integration-evidence。
- runner 报告记录 CPU／核数、内存、存储、Docker 镜像和限制、PG／Go、连接池和实际并发配置。使用 ubuntu-24.04 托管 runner，以实际报告冻结规格；不同环境指纹分开比较，不推断生产硬件等价。

B02 的现有 100,000 行／20 秒预算保持不变。容量初始化实际命中 read.ErrBudget 时报告 `known_background_budget_limit`，检查未发布新组合、未写可用时间；依赖该基线的后两场景报告 `blocked_by_initial_baseline`。不伪造成功基线。其他错误、缺失时间或摘要不符使测试失败。诊断工作流成功只表示诊断断言通过，不等于容量成功或 B10 性能达标。
