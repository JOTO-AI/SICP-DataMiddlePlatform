## 工作流与报告

`.github/workflows/build-performance.yml` 推送时保留诊断运行。手动选择 `acceptance=true`、`profile=false` 时，BP01—BP05 各 3 个独立 job，矩阵 `max-parallel=1`；每个 job 新建隔离数据库与卷。初始化准备完整运行但不冒充增量样本；准备时间和每轮端到端时间分别记录。BP02 严格每表 1 行，BP03 约 1%，BP04 增量 100% 替换，BP05 强制全量。

每次核心测量要求 `0 < T < 1800s`；目标摘要与独立生成器一致，生产可用探测在两份就绪和发布确认后记录终点。场景工件位于 `<BPxx>/<attempt>/stages.json`，公共工件包含 runner、进程与容器资源、日志、退出码。每轮额外采集 M/S 集群 WAL 差值（包含控制及采集写入，并非纯 COPY WAL）和四槽位新增读索引字节数。

`scripts/build_acceptance.py` 校验被测 SHA、profile 标记、退出码、固定规格、3 次完整样本、十四表规模/列宽/摘要/变化分布、真实计时边界及 M/S 独立 validate_copy 阶段。汇总全部样本的 min / median / max，不报告三样本 p95。任何缺失、失败或边界相等样本都拒绝通过。核心通过时仍输出 `full_acceptance_passed=false`，不能替代完整 B10。

Python 汇总器回归已加入常规 GitHub unit job；没有在本地执行。新增 Go/Playwright 测试分别由原 unit / integration / frontend job 执行。现有故障事务包装器补齐 COPY 转发，避免新导入路径使故障回归提前失败。
