# 系统自动运行与 ctl 移除方案

## 1. 目标和范围

系统启动后自动建立首份数据，之后持续调度同步。用户登录前端即可查看运行情况，并在需要时执行维护操作。日常运行不依赖打开网页、浏览器定时器或命令行提交任务。

删除 `sicpctl` 程序、Compose `ctl` 服务、`MANAGEMENT_URL` 和 Bash 管理命令。不要把被删除的管理命令换名后搬到另一个工具。部署时仍需容器平台启动服务；配置校验、数据库结构迁移、健康探测属于部署基础设施，不提供前端执行按钮。

## 2. 功能归属

| 原功能 | 新归属 | 前端呈现 | 本次改动 |
|---|---|---|---|
| 首次初始化 | worker 内部自动创建任务 | 查看记录、进度、失败原因，无初始化按钮 | 已实现 |
| 日常增量同步 | worker 持久调度，每两小时 | 查看记录及下次计划时间，无同步按钮 | 保留原调度，删除手动入口 |
| 强制全量 | 登录后的维护接口 | 确认后提交，有幂等保护 | 保留 |
| 失败重跑 | 登录后的维护接口 | 排除故障后提交原任务号 | 保留，支持失败的初始化任务 |
| 任务状态 | 后端只读接口 | 最近 50 条任务、按任务号详情、自动刷新 | 新增最近任务与调度状态 |
| 校验与发布 | worker 更新流水线 | 只显示执行阶段 | 保留自动执行 |
| 启动恢复 | worker 恢复流水线 | 展示服务状态、任务状态 | 始终先恢复，再调度 |
| 配置校验 | 服务启动时校验；部署预检使用服务自身 `--check-config` | 不提供触发按钮 | 替换 ctl validate |
| 数据库结构迁移 | Compose 一次性 `db-migrate` 任务 | 不提供触发按钮 | 独立部署程序，不能提交业务任务 |
| 健康探测 | 容器调用服务自身 `--healthcheck`；前端读取健康接口 | 运行总览 | 替换 ctl health |

前端的“更新任务”首先显示自动任务，维护区只保留强制全量和失败重跑。任务列表刷新只是读取状态，不会触发采集。

## 3. 自动初始化流程

1. 启动前完成配置校验、数据库迁移和依赖装配。
2. worker 取得已有进程锁，每轮优先核对执行所有权、未完成任务、待确认发布和活动路由。
3. 存在待恢复工作时继续恢复；Redis 路由丢失而控制库有已确认发布时走原路由恢复逻辑，不创建初始化任务。
4. 只有恢复决策为 idle 且不存在已确认活动数据时，才尝试自动初始化。
5. 在与其他准入共用的数据库执行锁内，复查：无任何历史任务、无数据组合、无发布记录、无源进度；四个槽位均为初始空状态、代次为零且未开放读取；调度行未使用且不在冷却；执行所有权未使用。
6. 检查通过后创建 `initialize` 任务，操作人记为 `scheduler`，幂等键为 `system-initialize-v1`。多个竞争请求最多创建一条记录。
7. 后续循环通过已有任务启动、采集、构建、质量校验、发布和进度确认流程执行，不绕过任何数据或恢复门禁。

有历史但没有活动数据的环境不算全新环境。控制数据库或 Redis 读取失败时拒绝初始化。已有控制事实不自动清理；物理数据处理仍经过原执行器的槽位与代次保护。该机制不负责修复人为删除控制库、拼接不一致备份等情况。

## 4. 失败、重启与调度

- 初始化任务在运行中重启：恢复原任务及其证据，不另建任务。
- 初始化任务明确失败：保留失败记录，不每秒重复创建全量采集任务。用户从前端查看失败任务并排除故障后重跑，新任务关联原失败任务。
- 初始化成功后：沿用持久化的两小时调度间隔，以实际任务开始时间计算下一次计划；重启不会重置时间。
- 日常同步失败：保留原失败记录，后续到期轮次仍由调度器驱动，也可以在前端执行失败重跑。
- 任务执行中、恢复未决或处于持久冷却期：禁止并行采集；计划时间可以过去，实际执行时间会顺延。
- 多次到期不补建一串历史任务；沿用原有单任务、调度版本检查和合并延后机制。
- 前端关闭、退出登录或会话过期：不影响后台任务、调度和恢复。

`/livez` 用于容器存活检查。初始化完成前、执行中或恢复期间的 `/readyz` 不就绪不等于容器已停止；部署不应因正常初始化时间长而不断重启 worker。

## 5. 接口和认证

删除 `POST /admin/v1/tasks/initialize` 和 `POST /admin/v1/tasks/sync`，不保留隐蔽兼容入口。

保留：

- `POST /admin/v1/tasks/force-full`
- `POST /admin/v1/tasks/{task_id}/rerun`
- `GET /admin/v1/tasks/{task_id}`

新增 `GET /admin/v1/tasks/`，返回最近 50 条受理记录及 `initialized`、`next_due_at`、`cooldown_until`、`interval_seconds`。列表只包含 task_id、mode、status、operator、accepted_at；详细进度和固定失败码沿用已有详情接口。较早记录可以继续按任务号查询。

所有管理读取和写入由后端校验管理员会话，写入继续校验 CSRF 和幂等键；前端不能指定操作人。接口不返回数据库凭据、原始源数据、会话标识或任务内部执行证据。

## 6. 部署与删除清单

- 删除 `cmd/sicpctl` 和对应管理工具测试。
- 镜像不再构建或复制 sicpctl；增加仅执行迁移的 `cmd/db-migrate`。
- 删除 Compose `ctl` 及其 tools profile；迁移账号继续只传给迁移容器。
- query/worker 镜像内的健康探测使用服务自身选项，部署预检也使用服务自身选项；不增加管理员命令入口。
- 从模板与本地 `.env` 删除 `MANAGEMENT_URL`；管理员账号密码只供 worker 控制台会话使用。
- 从 `scripts/sicp.sh` 删除 initialize、sync、force-full、rerun、task；保留部署、停止、重启、容器状态等生命周期操作。
- 更新 README、部署文档、管理 API 文档和前端指引，不再要求手动初始化。
- 将集成测试的手工初始化改为等待自动任务；定时同步测试在隔离数据库推进调度时间，不恢复生产手动同步接口。

## 7. 升级步骤

1. 停止应用容器并备份持久卷，保留数据库、日志、staging、targets、spool 的对应关系。
2. 更新代码，删除旧 `MANAGEMENT_URL`；保留管理员账号密码、源配置与其他现有配置。
3. 构建镜像，执行原有迁移部署任务并启动服务。此次不改历史迁移文件，不新增业务数据迁移。
4. 已初始化环境复用原数据、调度时间和任务历史；全新环境会开始访问所配置上游并自动初始化。
5. 登录前端查看自动任务和业务就绪状态。不要通过删除历史任务或清空控制库强行触发初始化。
6. 如果需要回退代码，停止新应用后使用旧镜像和匹配配置，保留新产生的任务记录；旧界面/旧脚本与新后端的移除接口不兼容，不混用部署。

## 8. 验收标准与测试

- 全新部署无需任何管理请求即可完成初始化，并可通过四个业务查询接口读取数据。
- 并发初始化竞争只产生一个任务；失败初始化与重启均不产生重复任务。
- 已有发布、任务、调度或槽位使用证据时不自动认定为空环境；读取和事务提交失败不视为初始化成功。
- 定时增量可更新有变化数据，也可完成无变化检查；恢复和冷却继续优先于调度。
- 原 initialize/sync POST 路由不可用，前端无这两个操作按钮。
- 登录后可以发现自动任务、查看详情、提交强制全量及失败重跑；未登录无法读取管理记录，缺失 CSRF 无法提交维护操作。
- Compose 不包含 ctl，镜像不包含 sicpctl，配置不再依赖 MANAGEMENT_URL；数据库迁移完成前应用不能启动。
- Go 单元测试、静态检查、构建、前端构建/浏览器测试、Compose 配置检查应通过；真实部署验收由 Linux Docker 集成测试执行。

本次实现对应以上方案。具体本地验证结果以变更交付记录为准；编译集成测试不代表已运行真实 PostgreSQL/Redis/Docker 场景。

2026-09-28 本地验证：Linux Go 全量单元测试通过；后续管理、控制存储、应用装配与 worker 变更的回归测试通过；Go vet、三个部署程序构建、集成测试编译通过；前端生产构建和 10 项 Playwright 测试通过；Compose 配置解析与模式检查、Bash 语法检查通过。当前本机 Docker 引擎不可连接，未执行真实容器集成测试和 race 检查，需由 Linux CI 补充。
