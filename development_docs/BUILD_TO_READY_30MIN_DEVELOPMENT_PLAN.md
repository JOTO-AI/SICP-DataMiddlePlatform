# 构建到可用 30 分钟专项开发计划

编写日期：2026-09-30，更新：2026-10-08。基准代码：`main / 1e8bc0e`。状态：**B01 三个小步的代码、测试和 GitHub 入口已补齐；待对应 SHA 的 CI 与容量工件，尚未验收**。开发分支：`perf/build-to-ready-30min`。实现、指标口径及验证状态见 [B01 开发记录](verification/B01.md)。

目标：在当前十四张表、约 259 万行的容量下，将“采集完成后的本地处理 → 两份副本就绪 → 正式发布 → 新版本实际可查询”控制在 **30 分钟以内**。所有表均有变化是主要验收场景，不能用无变化或只更新小表的成绩代替。

本计划沿用 [开发总计划](../DEVELOPMENT_PLAN.md) 和 [第一步详细开发计划](PHASE1_DETAILED_DEVELOPMENT_PLAN.md) 的“开发阶段／小步 → 对应单元测试 → 集成验收 → 证据记录”形式，使用独立编号 `B / BT / BI / BP`，不改写历史 P/T/I 验收结果。

其他依据：[项目架构](../PROJECT_ARCHITECTURE.md)、[字段与主键规划](../数据表结构与主键规划.md)、[查询契约](P06_QUERY_CONTRACT.md)、[自动运行方案](AUTOMATION_AND_CTL_REMOVAL.md)。现有源窗口、单表修复、部分采集失败保留及正式发布规则继续有效。

## 1. 目标、计时口径与完成条件

### 1.1 计时边界

- **起点 `build_started_at`：** 本轮所需的十四表采集／历史页复用全部成功并持久保存后，第一次进入本地封存处理的时刻。封存、保留引用、输入校验不能放到计时区间之外。
- **终点 `usable_at`：** 两份候选具有各自完整校验证据、正式发布事件已确认、成功进度已确认，且使用正常鉴权的四个已交付业务接口能查询到新组合。取这些条件最后一个成立的时刻。
- **总时长：** `T = usable_at - build_started_at < 1800 秒`。不能用 M 写入结束、候选 ready、第一次 `route_shift` 或 Redis 写入应答作为终点。
- 目标文件生成、两份写入、索引维护与统计信息更新、内容核对、业务检查、旧副本可读验证、切换排空、正式发布及可用性检查，凡在区间内发生均计入。
- 排除上游网络采集、等待人工修复未完成表、代码／镜像构建、一次性部署迁移。分别报告这些耗时，不能把每轮必做工作移到“迁移／准备”名下以缩短指标。
- 初始化、强制全量、有变化增量分别统计。主要目标是无故障正常轮次；故障恢复单独测试正确性和恢复耗时，不以故障轮次伪造正常性能。

## 3. 不得因加速而破坏的规则

1. 十四表组成一个完整目标；两份数据库分别核对，不拿文件校验代替数据库校验，不因 M 成功而跳过 S。
2. 保留缺键／null、前导零、数字 `3`／`3.0`／字符串 `"3"`、时间类型以及最新记录归并规则；业务表继续只存原定源字段，不使用 JSONB 改变原值语义。
3. 增量未返回的行仍保留，不能把“未出现在增量里”当删除；全量与强制全量的删除语义保持原规则。
4. 普通增量和手动增量保持相同时间窗口；成功水位不能变为导入结束、校验结束或发布时间。
5. 构建不能覆盖活动实例或有读者／未结束 SQL 的槽位。增量两次构建间的转移与排空顺序不能省略。
6. 任何复用证据必须绑定任务／所有权、组合、表版本、物理实例、槽位、代次及必要的校验实现版本。跨范围不能凭“之前成功过”直接复用。
7. 任一失败禁止本轮新组合发布，旧组合继续可用；发布应答未知按现有 outbox 恢复，不能删除未决记录强行重跑。
8. 保留完整数据和业务覆盖。不能悄悄把逐行核对改成抽样、只查行数、只执行 `SELECT 1`，或以业务请求第一页替代完整正确性检查。
9. 性能测试不用 `-race` 的时间作为正式成绩；race 另跑正确性回归。不得关闭 fsync、约束或改成不持久表取得成绩。

## 5. 详细开发任务与单元测试

### B01：建立计时与性能基准

- [x] **B01.01：记录真实阶段边界。** 在 worker/update/candidate/control 中记录封存、目标准备、每份写入、内容校验、索引校验、业务校验、旧组合验证、排空、发布、可用探测的开始／结束／失败时间。持久时间使用 UTC；进程内耗时使用单调时钟。重试记录 attempt，累计耗时与当前 attempt 分开。
  - Unit tests：**BT01-01** FakeClock 验证时间边界与重试累计；**BT01-02** 取消、失败及发布未确认时不写 `usable_at`；**BT01-03** 状态采集失败不伪造进度、不阻塞主任务无限等待。
- [x] **B01.02：增加低开销统计。** 统计行数、字节、批数、文件校验遍数、解码次数、SQL 次数、业务案例数、控制锁等待、缓冲峰值及临时磁盘峰值。按阶段聚合，禁止逐行写控制库。CPU／heap profile 和 EXPLAIN ANALYZE 只用于隔离的 GitHub 诊断任务。
  - Unit tests：**BT01-04** 多表／副本计数不串用；**BT01-05** 取消后无采集 goroutine 泄漏；**BT01-06** 日志只包含阶段、表和汇总指标，不包含源值、凭据。
- [x] **B01.03：生成可重复的大规模数据。** 增加确定性种子的容量生成器，产生十四表合法关联、上述规模及合理列宽；生成初始全量、各表 1% 变化、各表 100% 替换等输入和独立预期摘要。
  - Unit tests：**BT01-07** 固定种子确定性、各表至少一行变更、总行数及字节量校验；**BT01-08** 分布覆盖空值／宽字段／重复课程号／多教师，不退化为单一重复记录。

### B02：将后台校验预算与前台请求分离

- [x] **B02.01：设计后台流式预算。** `read.DefaultLimits()` 继续用于前台请求；为完整存储检查、案例枚举、后台业务计算分别装配预算。完整表行数依据可信 manifest 校验，并读取至 EOF／额外一行探测，不能命中上限就返回成功。以有界批缓冲、总任务取消和停滞监控限制资源，累计扫描字节不再误当常驻内存。
  - Unit tests：**BT02-01** 超过 100,000 行仍能完整核对；**BT02-02** 清单少报／多报一行均失败；**BT02-03** 计数溢出、异常巨大声明、重复游标拒绝；**BT02-04** 前台原有行数／时间限制不被放宽。
- [x] **B02.02：传播取消与阶段错误。** 后台预算耗尽、SQL 超时、内容不一致分别记录具体阶段和表；不记录敏感字段值。更新所有生产装配点，包括候选、已发布副本检查和无变化轮次，避免仅修一个入口。不能把所有业务请求的 Limits 一起改大。
  - Unit tests：**BT02-05** 新候选与旧副本均使用正确预算；**BT02-06** SQL 真实结束前不释放读取资格；**BT02-07** fake clock 超过前台 20 秒但仍在后台期限内正常，后台超时失败；**BT02-08** 失败不推进 ready、水位或 outbox。
  - 验收：大表通过校验不依靠无限内存；后台总超时是可诊断保护，不是“30 分钟内完成”的替代证明。资源预算的新配置需要同步配置解析、Compose 和文档。

### B03：修复游标排序索引与关联查询索引

- [x] **B03.01：补充匹配 `COLLATE "C"` 的游标索引。** 十四张表按实际主键建立 C 排序索引；保留原主键唯一约束和排序语义。使用新增 business migration（基于当前目录可命名 `business_003`，实施时核对冲突），不修改已应用 migration 的 SQL／checksum。
  - Unit tests：**BT03-01** 迁移覆盖十四张表及全部四槽位；**BT03-02** 索引列／排序规则与 `ReadMatching` 生成的 SQL 一致；**BT03-03** 重复迁移幂等、checksum 冲突拒绝。
- [x] **B03.02：增加高频等值过滤索引。** 根据调用路径与 EXPLAIN 选择组合索引：成绩 `(XH C, ID C)`、学生课表关系 `(XH C, ID C)`、排课 `(JXBH C, JHKCH C, PKH C)` 及 `(KKXND C, KKXQM C, PKH C)`；课程号等关联字段与其实际主键不同的，也评估“过滤列 C＋游标主键 C”。教师分隔工号不能直接用普通等值索引替代完整 token 匹配。
  - Unit tests：**BT03-04** 过滤排序 SQL 与索引定义匹配；**BT03-05** 中文、前导零、非 ASCII 主键跨页无重复漏行；**BT03-06** 多列过滤仍参数化，不允许调用方指定索引或 SQL。
- [x] **B03.03：明确迁移和统计信息策略。** 当前迁移器包在事务内，不能直接塞入 `CREATE INDEX CONCURRENTLY`。先采用受控部署窗口的事务迁移；如需在线迁移，单独实现并验证非事务恢复流程。批量导入后更新必要统计信息，耗时计入构建；报告新增索引对写入、WAL、磁盘的成本。

### B04：合并目标文件验证与逐行解析

- [x] **B04.01：设计一次消费完成多项核对的接口。** 为完整目标提供有边界的读取会话：解析并绑定 manifest／chunk 清单，流式消费同时核对 chunk 摘要、类型、主键顺序、行数、整表摘要；数据库比较使用同一条经过验证的记录，不重新 Canonical→Decode 同一对象。
  - Unit tests：**BT04-01** 与原实现对缺键、null、数字字面值、时间、未知字段的结果一致；**BT04-02** 位于最后一行的错误和未消费 EOF 不能被当成功；**BT04-03** 分块边界、重复主键、乱序、行数／摘要不符全部拒绝。
- [x] **B04.02：建立校验作用域和失效规则。** 缓存仅限当前进程内、固定目标／任务／所有权的工作组，不缓存跨重启的“成功布尔值”。先列出每遍校验防护的具体变更窗口，证明消费者核对覆盖后再删除前置完整扫描；保留需要的收尾复核。文件清单／chunk 被替换、截断或删除必须在 ready 前发现；若无法证明安全，则保留该遍扫描。
  - Unit tests：**BT04-04** 相同文件名但内容被换不能复用；**BT04-05** 已读 chunk 在组结束前被篡改仍失败；**BT04-06** 跨任务、跨组合、作用域过期及异常退出后证据不可用；**BT04-07** 取消等待所有消费者退出，无悬挂文件和泄漏。
- [x] **B04.03：精简重复校验并量化。** 优先将 `SourceStorage` 的前置全量校验并入必做的数据库逐行比较；保留结束保护。再评估 Builder 末尾与下一阶段相邻校验的合并。数据库每份全量核对独立执行，不能跨 M/S 复用行比较结果。
  - Unit tests：**BT04-08** 用读取计数器证明完整扫描次数下降，且损坏检测不变；**BT04-09** M 正常而 S 单行损坏时禁止发布；**BT04-10** 并发只读／GC 排斥规则 race 回归。
  - 验收：交付“原扫描 → 新扫描 → 覆盖的故障”对应表和解码／分配基准，不能只删除 Validate 调用后宣称优化完成。

### B05：提升导入与数据库内容核对吞吐

- [x] **B05.01：引入事务内流式 COPY 适配器。** 在 `internal/storage` 定义窄接口，由 `internal/adapters/postgres.go` 使用现有 pgx 能力实现；源列继续经过现有类型绑定。支持有界行数＋字节批次，避免为整表构造 SQL 参数或一次加载整表。

- [x] **B05.02：保留部分写入隔离与重试协议。** 先使表证据失效，再 TRUNCATE／分批 COPY，全部成功才记表完成。提交应答丢失不能盲目从下一批继续；无可信续点时重新构建该表。保留 INSERT 路径作为对照和显式回退，COPY 数据错误不能静默改用 INSERT 掩盖。
  - Unit tests：**BT05-05** 首批／中间批／最后提交失败均不 ready；**BT05-06** 重启后重建不产生重复行；**BT05-07** 旧活动槽位和未排空槽位写入被拒绝；**BT05-08** JSON 不能转 JSONB、主键重复仍报错。
- [x] **B05.03：优化数据库全量读取。** 优先在 B03 索引之上提高后台批量效率，减少重复元数据计算／事务开销；必要时增加后台专用有界流式读取接口。使用查询权限和固定槽位 handle，保持真实 SQL 生命周期登记，不能用 worker 写权限绕过读取控制。
  - Unit tests：**BT05-09** 全列比较发现等行数但内容不同、额外行、缺行；**BT05-10** 持续扫描可取消且退出后才释放资格；**BT05-11** 前台接口最大页大小和资源预算不受影响。
  - 验收：对比 INSERT/COPY 的耗时、CPU、WAL、内存和读取效率；两份副本各自按当前容量争取“写入含索引维护 4 分钟以内”，未达到则在 B10 之前继续剖析。

## 7. GitHub 性能验收

### 7.1 工作流设计

已新增 `.github/workflows/build-performance.yml`、`scripts/check-build-performance.sh` 和 `tests/integration/build_performance_test.go`；对应 SHA 的运行结果与工件仍待 GitHub 验证。

- 所有单元、race、集成、前端和性能测试只在 GitHub Actions 运行；本地仅编辑、格式化和文档／差异复核。
- 普通 PR 执行小规模正确性和扫描次数回归；完整容量使用 `workflow_dispatch` 与发布候选触发，固定被测 SHA，不混用不同版本镜像。
- 现有 integration job 30 分钟超时不足以容纳多轮容量验收。性能工作流为各场景拆独立 job，每个单轮 job 建议 90 分钟作“依赖准备＋生成＋诊断”上限，**被测 T 仍必须小于 1800 秒**。
- 不同重复轮次不能在同一台测试机上同时争用资源。隔离数据库、卷、Redis 前缀；单个性能 job 不在后台另跑单测／镜像构建。
- 测量前准备完整采集页和持久证据；测试开始调用真实封存及后续 worker 流程。增量场景先建立并验证旧组合，但不计入下一轮构建时间，准备耗时另报。
- 正式性能运行不启用 race 或持续 profiler；另跑剖析任务定位瓶颈。记录页缓存条件，区分正常热缓存与全新实例／卷的冷启动近似，不随意清宿主缓存。
- CI 未启动、超时、跳过、错误结束都不能计入“达标”样本。GitHub 账单／额度问题先恢复；不因此改为本地测试或勾选通过。

### 7.3 通过条件与证据

2. 所有 BT／BI 正确性测试通过；新方案与参考实现的最终清单摘要、两份库中数据及四接口结果一致。
3. 两份副本的业务和存储校验证据完整；性能达标但省略校验一律不通过。
4. 无 OOM、无依赖交换空间掩盖内存超限、缓冲／临时盘／连接数均在 B01 冻结的预算内；记录索引额外空间和导入 WAL。
5. 同一 runner 上保留改动前的基准或“为何无法完成”的明确失败结果；用逐阶段对照证明收益，不能用老版本失败耗时计算虚假的加速倍数。
6. Artifact 至少包含：环境规格、SHA／镜像标识、fixture seed／摘要、逐阶段和逐表统计、正常入口探测结果、EXPLAIN JSON、资源曲线、脱敏日志、失败重试记录。稳定路径建议 `artifacts/build-performance/<scenario>/<attempt>/`。

## 8. 发布、回退与不达标处理

- 每小步完成代码和测试后先 review，再按当前会话授权提交／推送；发布候选必须关联对应 SHA 的完整 CI 证据。文档中的流程不替代用户已经给出的授权，也不自动授权生产部署。
- 先部署必要的新索引及配置，再部署兼容读取既有目标格式的新二进制。不得修改历史迁移；新增索引通常可在二进制回退时保留，空间清理另行处理。
- 目标格式或就绪证据版本若变化，先定义兼容读取／失效策略；不能把旧证据误认为新算法已校验，也不能强行删除旧目标解决兼容问题。
- 优化失败时可退回显式 INSERT、串行和完整扫描路径，但后台预算与 C 排序索引等正确性修复不能回退成已知必败行为；回退后性能目标需重新标识为未达标。
- 未发布候选失败不影响旧组合；初始化失败保持未就绪；已发布但进度待确认遵守原恢复协议，不用回退版本撤销发布事实。
- 若 B03—B07 后已达 30 分钟目标，可不启用高风险并发，B08 保留锁诊断和回归验证。若仍不达标，按 profile 排名继续优化并重复 BP，不靠扩大并发、减少校验或改计时口径过关。

## 9. 本轮不作为达标前提的后续方向

**数据库行级增量写入**可进一步减少变化较少时的导入量，但不作为“所有表全部变化”场景的主要保证。当前槽位可能为空或落后多轮，不能直接把相对活动版本的变化写到任意槽位；后续专项需要按每槽位可信基线计算差异、处理全量删除、崩溃恢复和摘要重建后才可启用。

**M/S 无条件同时构建、跳过 S 校验、抽样替代完整校验、延迟到发布后再验证**不属于本计划方案。初始化并行只在 B08 证明隔离和资源条件后评估，正常增量继续遵守切换排空协议。
