# 构建专项升级与回退

本分支尚待完整 GitHub 正确性与容量验收，不表示生产部署已获准或已达 30 分钟。发布候选必须固定 SHA 和同一版本镜像，并关联对应 Actions 工件；当前状态见 [B10](verification/B10.md)。

## 受控升级

1. 确认数据库与持久卷备份可恢复，记录当前镜像、迁移版本、活动组合及未决 outbox。让正在执行的 worker/SQL 按既有协议退出；不要清空所有权或读者记录强行排空。
2. 在受控窗口停止相关服务并应用新增 `business_003`。使用既有 `bash scripts/sicp.sh migrate`，对 M0/M1/S0/S1 运行事务迁移；不要编辑已经应用的 business_001/002，不改 checksum。索引建设可能持有/等待表锁，窗口长度须按实际数据量评估。
3. 迁移失败应先确认事务回滚和真实 SQL 结束，再用同一镜像重试。不得手工写迁移成功记录。确认十四表 C 游标、四个关联索引及 worker 的 MAINTAIN 权限；业务 query 账号保持只读。
4. 配置 `BUILD_CHECK_TIMEOUT=30m`（1s—1h，每阶段保护）和 `BUILD_IMPORT_MODE=copy`（copy/insert）。现有 `BUILD_TABLE_CONCURRENCY` 仅控制文件构建，数据库物理导入仍串行。索引维护和每表 ANALYZE 均计入构建时间。
5. 使用同 SHA 的 worker/query 镜像启动，让原恢复流程处理未决任务。确认旧/新活动组合、两份校验证据、正式发布与进度确认，使用真实鉴权业务入口探测；不能把 `/livez` 或行进度 100% 当作可用。

## 失败与回退

- COPY 类型、主键或提交失败不会自动换 INSERT。需要对照时显式改 `BUILD_IMPORT_MODE=insert` 并重建 worker 容器；未知提交结果由持久状态决定重建，不能凭展示行数续写下一批。
- 候选失败保持旧发布版本；初始化失败保持未就绪。已发布但进度未确认时继续原 outbox/恢复协议，不用回退二进制撤销发布事实。
- 回退二进制时可保留 business_003 索引与授权，不降级/删除业务表。目标格式未改变；仍需保留历史目标、staging 和恢复引用，不删卷解决兼容问题。
- 不回退到后台 10 万行/20 秒的已知大表失败预算；如需回退其他优化，应选择包含 B02/B03 正确性修复的版本。INSERT 与原完整排序仍有参考路径，但不提供未经实现的配置开关。
- 当前未启用额外数据库并发。若后续新增并发，必须单独验证总资源预算、接管与 SQL 排空，再更新此说明。
- 回退后重新记录性能状态；此前样本不能证明回退版本仍达标。完整 BP/BI 验收未通过前，不调整对外 SLA。

## 可观测性

前端显示表、副本、成功处理行/案例、已提交批次、阶段与任务耗时，以及独立的心跳/真实进展时间。未知总量不显示百分比；45 秒无进展提示与心跳失联区分，终态计时停止。当前执行器内的阶段重试累计与跨进程持久事件分开解释。任何展示字段都不能授权发布、接管或水位推进。

GitHub 手动核心验收选择 `acceptance=true`、`profile=false`，覆盖 BP01—BP06 和 BP08 冷/暖近似各三轮；`acceptance=false` 时可通过 `scenario` 选择 BP09 或 BP10-double/wide/hot 等诊断入口。诊断 profile 单独运行。下载所有场景与次数的工件，保留失败、环境规格、WAL/索引空间和资源曲线。BP07 在线负载及完整资源验收未齐，核心汇总结果不是完整 B10 通过结论。
