## 1. 需求

### 1.1 本阶段交付范围

- 服务基础：Go 查询服务和 Go 更新服务，支持配置加载、健康检查、优雅退出和 Linux 容器运行。
- 数据更新：十四类源数据接入、原值保存、比较合并、双份构建、版本发布、调度与恢复。
- 业务接口：接口 4 学生成绩、接口 5 批量成绩、接口 6 学生课表、接口 7 教师课表。
- 公共查询能力：鉴权、参数处理、查询缓存、读取协调及分页一致性。
- 运行管理：日志持久化与补投、未知字段邮件通知、必要的管理后端。
- 质量要求：每个开发任务均须具备通过的单元测试、适用集成验证和代码复核记录。

接口 1、2、3、8、9 和日志/运维前端留在第二步；生产规模压测与上线留在第三步。本阶段仍同步全部十四类数据；所有 T、I 测试均使用仓库 Mock 数据，不调用真实上游、不读取真实人员样本、不向外部邮箱发送邮件。I 系列在开发全部完成后，用 Mock 数据驱动本地隔离的数据库、Redis 和双服务链路。

执行环境统一为 Linux：单元测试及自动化检查在 GitHub Actions 的 Linux runner 上运行，最终代码和容器部署到 Linux。集成测试也全部在 GitHub Actions 的 Linux runner 上执行，本地只编辑和静态检查；仍遵守全部 P/T 完成后才启动的顺序。CI、构建和部署使用同一确定的 Go 版本；脚本采用 Bash，路径大小写、文件权限、进程信号和时区行为按 Linux 验证。

### 1.2 四个接口的需求

| 接口 | POST 路径 | 主要行为 |
| --- | --- | --- |
| 4 学生成绩 | /api/v1/sicp/students/grades/query | 学号必填；默认先确定最近有成绩的学期再筛选；支持学年/学期、all、课程及分数条件；过滤后计数分页 |
| 5 批量成绩 | /api/v1/sicp/students/grades/batch-query | 学年或 all 必填；学号集合、学生院系、行政班与课程条件组合；total 为成绩条数 |
| 6 学生课表 | /api/v1/sicp/students/timetable/query | 从本人课程关系按 JXBH/JHKCH 及所选学期匹配排课；完整返回，不按行政班猜归属 |
| 7 教师课表 | /api/v1/sicp/staff/timetable/query | 从排课直接查询，拆分后完整工号匹配；课程/教学班筛选，多教师不重复返回同一安排 |

所有字段、必填、默认值和 null 规则逐项遵守接口设计。成绩学分取成绩表 XF，学生归属取最新学籍；可选关联缺失保留主记录和已有编号。课表日期取 SKRQ、周次取 ZC，工号和姓名数组不强制下标配对。读取失败与正常空列表必须区分。

业务接口的字段、类型、参数和行为以 sicp-api-design.md 为准；本计划或其他实现文档与其不一致时，应修正实现计划和测试预期。该文档明确留待讨论的事项确认后再实施。本阶段按固定接口规则开发；未来查询规则调整通过软件新版本发布处理，本阶段不开发运行时规则切换或规则升级流程。

### 1.3 共用架构约束

这些约束用于验收，避免在每个任务下重复抄写相同检查项。

| 范围 | 必须保持的规则 |
| --- | --- |

| 原值 | 保留前导零、空格、数字 token；区分数字 3、3.0 和字符串 3；缺键/null 按列类型处理，源比较证据保留 |
| 合并 | 按确认主键整行替换；学籍及两张通讯表先按最新记录规则归并，其余表重复键报错；增量未返回旧行保留，不做全表删除差集 |
| 窗口 | 增量从各表成功进度减默认五分钟到任务固定开始时间；全量所有页/重试完全省略 startTime/endTime |
| 发布 | 十四类完整、两份候选全部通过才发布；先 S 新候选→确认 S 上旧组合完整可读→转 S 旧组合查询→排空 M→M 新候选→在 S 发布 |

| 状态 | 转移和发布分别持久化；不假定 Redis 与各库存在普通跨库原子事务；失败/未决不推进成功进度 |
| 特殊分支 | 普通无变化复用组合；强制全量同内容也双份重建发布；构建和大量清理在非查询实例执行 |

| 日志 | 缓冲前脱敏，持久补投有界；未知字段通知待发事实保存在固定控制区，不依赖日志 PG 存活 |

学籍、学生通讯和教职工通讯的最新记录规则按字段规划第 8.2.1 节执行：先按已确认的源业务更新时间比较，无该字段时按解析后的 ETL_TIME 比较；现有三表没有可用业务更新时间，不自行增加源字段。同批和跨轮均选择整条最新记录，迟到旧记录不覆盖新值；完全相同记录可归并，同优先时间内容冲突或多条记录的时间无法比较则报错。分页完整性按归并前源记录数核对，当前表仍每人一条；课程等其他表不能套用此例外。

## 2. 方案

### 2.1 开发与核对方式

P01—P15 保留阶段名称、依赖和整体目标；第 2.2 节的 `Pxx.yy` 是实际工作单元。每个子步骤的 P 复选框表示实现、对应测试代码、必要配置/文档和代码复核已完成；单测通过只在对应 T 项勾选。开始下一子步骤还必须满足本步对应 T 子用例和已实现单测回归在 GitHub CI 通过。P 总框在全部开发子项完成后勾选，T 总框在该组全部场景实际通过后勾选；两个总框都满足才进入依赖阶段，跨线依赖还须满足整分支合并及 main CI 门槛，同线按已验证分支继续。I01—I06 仍在全部 P/T 完成后执行。

拆分和提交规则：

1. 每步交付一个可描述的行为、组件或边界，包含它的正常/错误路径及必要测试；不按文件数量机械切分，也不把一项功能的实现和测试分到两次开发步骤。
2. 当前步骤依赖已完成步骤；未来模块通过明确的接口和 Mock 替身隔离。本步代码须能编译、被实际测试且不误报业务就绪，不能提交需要下一步才能修好的中间状态。
3. 一个子步骤对应一次独立提交和 push 检查点，不把多个未验证步骤堆到一次 push。顺序为开发和测试代码 → code review/修复 → commit → push → GitHub CI；CI 失败只修复当前步骤并追加聚焦的修复提交/push，直至通过，再进入下一步。修复重推不算新的功能步骤。
4. 单元测试仅在 GitHub Actions Linux runner 上执行，不在本地运行。在当前开发分支逐步 push 触发 CI，以该次提交作为检查点；若还需合入独立交付分支，须等云端检查通过。不要求为每个小步骤另建分支，也不把“先本地跑测试”作为门槛。
5. commit message 必须以 `type: ` 开头，并直接描述实际改动，例如 `feat: validate service configuration and redact invalid values`、`fix: close the listener before releasing service dependencies`。Pxx/Pxx.yy 仅用于计划与证据关联，不能代替具体提交内容；必要时在正文补充行为、边界与验证方式。
6. 每步保持可单独回退：本步新增代码/测试/配置一起回退，前序已验证步骤仍可构建；迁移采用可独立识别的版本，不覆盖已应用迁移。代码回退与已执行数据迁移的恢复分别说明，涉及数据/发布事实时不得宣称 git revert 会自动还原运行状态。后续步骤已依赖本步时，须按依赖顺序回退或提交修复。
7. 每步同步必要说明与复核结果；阶段末只汇总已有证据，不新增一个“集中补测试/集中复核”的大步骤。镜像构建、Bash 语法和权限检查是构建/静态检查，实际数据库、跨进程与容器运行效果由 I 系列验收。

开发记录保存到 development_docs/verification/Pxx.md，按 Pxx.yy 记录变更文件、决策、代码复核、commit SHA、push 分支及回退边界；单测记录保存到 Txx.md，逐步关联 Mock 场景、实际测试名/编号、命令/退出码、通过/失败/跳过数、GitHub Actions 链接和 artifact。集成记录仍保存到 Ixx.md。未运行、跳过或“no tests to run”不算通过；push 后产生的运行链接可在下一次必要文档更新或阶段记录汇总时补录，不为改一个结果链接无限触发提交循环。

工程沿用架构中的 cmd、internal、migrations、deploy；单测与源码邻接，共享 Mock 加载器及替身放 internal/testkit，集成测试放 tests/integration。时钟、随机源、HTTP、存储、缓存、文件与邮件通过明确边界注入。第 3 部分维护测试规则和场景清单；夹具准备、测试编写与执行归属每个开发子步骤，不推迟到阶段末。

### 2.2 分阶段开发步骤与对应 unit tests

每个 `Pxx.yy` 是一个开发、复核和推送单元，按阶段编号及阶段内编号串行执行。阶段依赖沿用原计划；阶段内默认依赖前面已通过的步骤，未来模块用显式 Mock 接口隔离。各步列出的 T 编号指向第 3.2 节的独立断言，不是只写一个测试名称即算完成。同一 T 覆盖多个步骤时，在测试记录中列明本步子用例和后续回归范围，整条 T 的全部断言通过后才勾选。

每步同时提交实现、对应测试代码、必要配置/迁移与文档；复核通过后单独 push，GitHub 单测和适用构建检查通过后才能开始下一步。纯镜像、脚本和权限检查另列为构建检查，不冒充 unit tests。所有步骤均执行第 2.1 节的完成与回退规则，阶段末不再集中补测试或复核。

**Pxx.yy 负责一次完整开发步骤，Txx 的指定场景检验该步骤；I 系列检验已完成模块之间的集成。** P 与 T 均保留 15 个阶段组，一一对应；Pxx.yy 不增加顶层阶段数量。第 2.2 节逐步列出测试归属，第 3.2 节保留原有 T 编号并补充缺失断言。

阶段按并行方案的依赖分线执行，每阶段内部按 Pxx.01、Pxx.02 等逐步开发、复核、推送并在 GitHub 验证；失败时留在当前步骤修复，同时回归受影响的已实现 T。各阶段末核对该 T 组是否全部完成，整条线完成后合并分支并验证 main。I01—I06 不在中途执行；全部 P/T 完成后顺序执行，I 失败时修复相关代码、在 GitHub 回归受影响 T，再重跑相关 I。

所有测试的数据都来自仓库 mock_data 或新增的合成 Mock 夹具。T 通过 Mock 接口替代数据库、Redis、文件、HTTP 和邮件依赖，存储结果及调用记录保存在内存中，结合 FakeClock 检验实现的输出、状态变化和副作用，不启动真实数据库或 Redis；模拟重启时可复用代表持久状态的内存存储，再重建待测组件。I 将同样的 Mock 数据加载到本地隔离 PG/Redis，以实际服务及适配器验证集成行为。**使用本地数据库不改变数据仍是 Mock 的要求。** 测试不调用真实源、不读取 source_samples 中的真实人员样本、不向外部邮箱发信。

Mock 只替换待测模块的外部依赖，不替换本次需要验证的实现。例如 T02 执行实际仓储/事务控制代码，将更下层的数据库执行接口替换为内存替身；T07 执行实际成绩查询代码，将仓储替换为 Mock。替身记录参数、调用顺序及写入状态，不预先返回待测模块的完整答案。T 中的持久化、回滚和并发断言验证调用与状态处理逻辑，真实数据库事务、跨进程竞争和进程退出后的文件持久性由 I 验证。

现有 MockSource 是离线读取工具，没有现成 HTTP 服务。集成测试准备时需要提供本地 HTTP 包装或响应回放器，返回现有 requests.json、responses 和快照对应的数据；邮件使用本地 Mock 接收端。控制状态、配置、缓存、权限及故障也使用合成夹具。

GitHub Actions 的常规 Linux 作业运行已实现的 T 用例及构建检查；每个子步骤的验收以该次 push 对应作业实际执行并通过为依据。每次相关修改回归已实现单测，不能因仅执行当前 T 子集而遗漏已有模块回归，也不能为未来未实现的场景添加空测试冒充通过。I 使用独立作业和显式 integration 标签，全部 P/T 完成前不触发；启用后先依赖单测作业成功，再启动同一 Linux runner 上的隔离服务。工作流保留逐用例结果、退出码和失败日志，清理临时服务与卷。P01 的 Linux CI 已建立并执行通过，证据见 verification/T01.md；未来场景仍为待实现。

测试准备随使用它的子步骤完成，不新增一个集中准备/推送的大步骤。共享源 Mock 加载器从 P03.01 引入，配置/控制/仓储夹具从 P02 对应步骤引入，业务和故障夹具由使用它的步骤补齐；FakeClock 和基础 CI 沿用 P01 成果并按需扩展。I 专用包装器、隔离环境及标签只在全部 P/T 完成后的集成准备中接入。以下复选框是跨阶段准备项的汇总，未覆盖全部要求时保持未完成：

- [ ] 为 tests/integration 下所有集成测试及专用环境启动文件添加文件顶部构建约束 `//go:build integration`，与 package 声明间保留空行；包括 TestMain 和专用辅助文件，普通单测不启动集成依赖。
- [ ] 核对普通单测命令及其环境没有启用 integration 标签，默认测试清单不包含 I 系列；全部 P/T 完成后，显式启用该标签，核对 I 系列用例被实际发现并执行。
- [ ] 每个场景都有独立测试名和结果；同一规则的多个输入可参数化，但不能把预算、分页、取消等不同规则合并为一个通过结果。

- [ ] 在故障注入前注册清理动作：T 清理内存状态、替身和后台任务；I 恢复权限及故障配置、释放连接并清理隔离资源。断言失败仍执行清理；进程崩溃或被强制终止时，由外层测试运行器回收环境。恢复失败记为失败并隔离环境，禁止后续用例复用污染状态。
- [ ] 连续流程仅在单个明确标记的用例内部共享状态，仍从自己的基线开始并在结束后清理；例如 I05-07、I06-06。恢复类用例自行建立故障前置状态，不隐式承接其他编号用例的执行结果。

每个 T 子项是可单独勾选的场景，格式为“输入或前置条件 → 操作后的预期”。组总框只能在所有子项实际通过后勾选；没有运行、未实现或跳过不算通过。T 的未来状态可由夹具注入，例如 T11 注入转移后的活动位置，不提前依赖 P13 的完整编排。

实施时按字段矩阵为四接口的每个请求参数和响应字段绑定测试断言；共用行为可由参数化用例覆盖，但各输入须有独立结果。涉及“按确认规则”的用例，应先在对应 P 记录具体决定，再把预期细化为确定的字段值或错误类别后执行。

现有业务场景优先复用：空值/数字、full_row_merge、重排、empty_incremental、repeat_incremental、source_delete_incremental/full、分页故障、成绩最近学期、multiple_schedules_teachers、cross_term_ambiguity，以及全量/增量未知字段场景。新增夹具不覆盖或改写现有样例。

测试命名建议为 TestT07_01、TestI04_01 等，编号与下方清单一致；跨步骤细分可用 TestT07_01/子场景 并记录所属步骤。集成测试由上述构建约束排除在默认构建之外，仅放入 tests/integration 目录或仅在执行命令中增加标签不足以实现隔离。以下是 GitHub Actions 内的执行入口，不是本地单测指令；未来场景没有声称实现或通过：

~~~bash
# 当前子步骤：按映射选择已实现的用例，确认实际发现并运行；不能代替完整回归。
go test ./... -run '^TestT07_' -count=1 -v

# GitHub Actions Linux 常规作业：回归所有已实现单测；全部 P/T 完成后也执行此项。

# Linux runner 配备 C 编译器，在相关包实现后执行 race 检查。
~~~
