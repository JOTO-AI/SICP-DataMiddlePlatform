## 1. 需求

### 1.1 本阶段交付范围

- 服务基础：Go 查询服务和 Go 更新服务，支持配置加载、健康检查、优雅退出和 Linux 容器运行。
- 数据更新：十四类源数据接入、原值保存、比较合并、双份构建、版本发布、调度与恢复。
- 业务接口：接口 4 学生成绩、接口 5 批量成绩、接口 6 学生课表、接口 7 教师课表。
- 公共查询能力：鉴权、参数处理、查询缓存、读取协调及分页一致性。
- 运行管理：日志持久化与补投、未知字段邮件通知、必要的管理后端。
- 质量要求：每个开发任务均须具备通过的单元测试、适用集成验证和代码复核记录。

接口 1、2、3、8、9 和日志/运维前端留在第二步；生产规模压测与上线留在第三步。本阶段仍同步全部十四类数据；所有 T、I 测试均使用仓库 Mock 数据，不调用真实上游、不读取真实人员样本、不向外部邮箱发送邮件。I 系列在开发全部完成后，用 Mock 数据驱动本地隔离的数据库、Redis 和双服务链路。

执行环境统一为 Linux：单元测试及自动化检查在 GitHub Actions 的 Linux runner 上运行，最终代码和容器部署到 Linux。集成测试也在 Linux 环境执行，仍遵守全部 P/T 完成后才启动的顺序。CI、构建和部署使用同一确定的 Go 版本；脚本采用 Bash，路径大小写、文件权限、进程信号和时区行为按 Linux 验证。

### 1.2 四个接口的需求

| 接口 | POST 路径 | 主要行为 |
| --- | --- | --- |
| 4 学生成绩 | /api/v1/sicp/students/grades/query | 学号必填；默认先确定最近有成绩的学期再筛选；支持学年/学期、all、课程及分数条件；过滤后计数分页 |
| 5 批量成绩 | /api/v1/sicp/students/grades/batch-query | 学年或 all 必填；学号集合、学生院系、行政班与课程条件组合；total 为成绩条数 |
| 6 学生课表 | /api/v1/sicp/students/timetable/query | 从本人课程关系按 JXBH/JHKCH 及所选学期匹配排课；完整返回，不按行政班猜归属 |
| 7 教师课表 | /api/v1/sicp/staff/timetable/query | 从排课直接查询，拆分后完整工号匹配；课程/教学班筛选，多教师不重复返回同一安排 |

所有字段、必填、默认值和 null 规则逐项遵守接口设计。成绩学分取成绩表 XF，学生归属取最新学籍；可选关联缺失保留主记录和已有编号。课表日期取 SKRQ、周次取 ZC，工号和姓名数组不强制下标配对。读取失败与正常空列表必须区分。

业务接口的字段、类型、参数和行为以 sicp-api-design.md 为准；本计划或其他实现文档与其不一致时，应修正实现计划和测试预期。该文档明确留待讨论的事项确认后再实施。本阶段按固定接口规则开发；未来查询规则调整通过软件新版本发布处理，本阶段不开发运行时规则切换或规则升级流程。

### 1.3 共用架构约束

这些约束用于验收，避免在每个任务下重复抄写相同检查项。

| 范围 | 必须保持的规则 |
| --- | --- |
| 存储 | M/S 两实例各两完整槽位；十四表共 256 TEXT、15 JSON、3 TIMESTAMP WITHOUT TIME ZONE 源字段；不增加派生业务表或 raw/转换双份存储 |
| 原值 | 保留前导零、空格、数字 token；区分数字 3、3.0 和字符串 3；缺键/null 按列类型处理，源比较证据保留 |
| 合并 | 按确认主键整行替换；学籍及两张通讯表先按最新记录规则归并，其余表重复键报错；增量未返回旧行保留，不做全表删除差集 |
| 窗口 | 增量从各表成功进度减默认五分钟到任务固定开始时间；全量所有页/重试完全省略 startTime/endTime |
| 发布 | 十四类完整、两份候选全部通过才发布；先 S 新候选→确认 S 上旧组合完整可读→转 S 旧组合查询→排空 M→M 新候选→在 S 发布 |
| 协调 | 每请求固定实例/槽位/代次/组合；HTTP 超时、失联或租约过期不等于实际 SQL 排空；控制区不随业务槽位覆盖 |
| 状态 | 转移和发布分别持久化；不假定 Redis 与各库存在普通跨库原子事务；失败/未决不推进成功进度 |
| 特殊分支 | 普通无变化复用组合；强制全量同内容也双份重建发布；构建和大量清理在非查询实例执行 |
| 时间 | 源时间、窗口进度、任务起止、就绪、发布和检查时间分别记录；不以调用时间冒充 synced_at |
| 鉴权 | 读缓存之前校验固定 API key；个人查询范围由可信工具/MCP 层约束，管理认证独立 |
| 日志 | 缓冲前脱敏，持久补投有界；未知字段通知待发事实保存在固定控制区，不依赖日志 PG 存活 |

学籍、学生通讯和教职工通讯的最新记录规则按字段规划第 8.2.1 节执行：先按已确认的源业务更新时间比较，无该字段时按解析后的 ETL_TIME 比较；现有三表没有可用业务更新时间，不自行增加源字段。同批和跨轮均选择整条最新记录，迟到旧记录不覆盖新值；完全相同记录可归并，同优先时间内容冲突或多条记录的时间无法比较则报错。分页完整性按归并前源记录数核对，当前表仍每人一条；课程等其他表不能套用此例外。

## 2. 方案

### 2.1 开发与核对方式

P01—P15 只列开发内容，不包含运行测试或测试通过项。P 总框表示该任务代码、配置、文档及代码复核已完成；T01—T15 分别检验同编号 P 的实现，测试结果只勾选在 T 中。对应 T 未通过时修复该 P，不进入依赖它的下一开发任务。I01—I06 统一在所有 P、T 完成后执行，不作为中途 P 的完成条件。

开发记录保存到 development_docs/verification/Pxx.md，记录变更文件、决策和代码复核；单测记录保存到 Txx.md，集成记录保存到 Ixx.md，记录 Mock 场景、用例编号、命令/退出码、通过/失败/跳过数及证据。未运行、跳过或“no tests to run”不算测试通过。

工程沿用架构中的 cmd、internal、migrations、deploy；单测与源码邻接，共享 Mock 加载器及替身放 internal/testkit，集成测试放 tests/integration。时钟、随机源、HTTP、存储、缓存、文件与邮件通过明确边界注入。测试数据准备与执行统一安排在第 3 部分。

## 3. 单元测试

### 3.1 P、T、I 的对应关系与 Mock 数据规则

**Pxx 负责开发，Txx 检验同一个 Pxx；I 系列检验已完成模块之间的集成。** P 与 T 均保留 15 组，一一对应；拆分的是 T/I 组内的独立场景，不增加 P 的任务数量。

执行顺序固定为：P01 → T01 → P02 → T02 → …… → P15 → T15 → I01 → I02 → I03 → I04 → I05 → I06。I 不在中途执行，也不作为任何 P 的开发完成项。T 失败时修复对应 P 并重跑该 T；I 失败时定位并修复相关 P、回归受影响 T，再重跑相关 I。

所有测试的数据都来自仓库 mock_data 或新增的合成 Mock 夹具。T 通过 Mock 接口替代数据库、Redis、文件、HTTP 和邮件依赖，存储结果及调用记录保存在内存中，结合 FakeClock 检验实现的输出、状态变化和副作用，不启动真实数据库或 Redis；模拟重启时可复用代表持久状态的内存存储，再重建待测组件。I 将同样的 Mock 数据加载到本地隔离 PG/Redis，以实际服务及适配器验证集成行为。**使用本地数据库不改变数据仍是 Mock 的要求。** 测试不调用真实源、不读取 source_samples 中的真实人员样本、不向外部邮箱发信。

Mock 只替换待测模块的外部依赖，不替换本次需要验证的实现。例如 T02 执行实际仓储/事务控制代码，将更下层的数据库执行接口替换为内存替身；T07 执行实际成绩查询代码，将仓储替换为 Mock。替身记录参数、调用顺序及写入状态，不预先返回待测模块的完整答案。T 中的持久化、回滚和并发断言验证调用与状态处理逻辑，真实数据库事务、跨进程竞争和进程退出后的文件持久性由 I 验证。

现有 MockSource 是离线读取工具，没有现成 HTTP 服务。集成测试准备时需要提供本地 HTTP 包装或响应回放器，返回现有 requests.json、responses 和快照对应的数据；邮件使用本地 Mock 接收端。控制状态、配置、缓存、权限及故障也使用合成夹具。

GitHub Actions 的常规 Linux 作业只运行已实现的 T 用例及构建检查；对应 P 的验收以该作业实际执行并通过为依据。每次相关修改回归已实现的单测，不能因仅执行当前 T 组而遗漏已有模块回归。I 使用独立作业和显式 integration 标签，全部 P/T 完成前不触发；启用后先依赖单测作业成功，再启动同一 Linux runner 上的隔离服务。工作流保留逐用例结果、退出码和失败日志，清理临时服务与卷。当前文档只规划工作流，尚未在 GitHub 执行。

每个 T 子项是可单独勾选的场景，格式为“输入或前置条件 → 操作后的预期”。组总框只能在所有子项实际通过后勾选；没有运行、未实现或跳过不算通过。T 的未来状态可由夹具注入，例如 T11 注入转移后的活动位置，不提前依赖 P13 的完整编排。

实施时按字段矩阵为四接口的每个请求参数和响应字段绑定测试断言；共用行为可由参数化用例覆盖，但各输入须有独立结果。涉及“按确认规则”的用例，应先在对应 P 记录具体决定，再把预期细化为确定的字段值或错误类别后执行。

现有业务场景优先复用：空值/数字、full_row_merge、重排、empty_incremental、repeat_incremental、source_delete_incremental/full、分页故障、成绩最近学期、multiple_schedules_teachers、cross_term_ambiguity，以及全量/增量未知字段场景。新增夹具不覆盖或改写现有样例。
